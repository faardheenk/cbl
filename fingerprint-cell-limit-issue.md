# Fingerprint Cell Size Limit Issue

## Problem

When saving moves, the app writes match history to `history.xlsx` (stored in `Matrix/{insurer}/` on SharePoint). Each history entry stores fingerprint arrays as JSON strings in individual Excel cells:

```
CblFingerprints: JSON.stringify(entry.cblFingerprints)
InsurerFingerprints: JSON.stringify(entry.insurerFingerprints)
TargetCblFingerprints: JSON.stringify(entry.targetCblFingerprints)
...etc
```

Each fingerprint is generated by concatenating **all non-metadata column values** of a row, joined by `|`. When a move involves rows with many columns or long values, the JSON-serialized array stored in a single Excel cell can exceed the **XLSX cell character limit of 32,767 characters**, causing the error:

```
text length must not exceed 32727 characters
```

## Current Fingerprint Flow

1. **Backend** generates `_fingerprint` and `_fingerprint_INSURER` fields during preprocessing and attaches them to each row.
2. **Frontend** uses `getCanonicalCblFingerprint` / `getCanonicalInsurerFingerprint` to read those backend-generated values.
3. **Frontend** also has its own `generateFingerprint` function that concatenates all non-excluded column values — this is used as a fallback and for match history entries.
4. **Frontend** saves fingerprint arrays to `history.xlsx` and reads them back via `readMatchHistory` to replay past moves.

## Proposed Solutions

### Option 1: Hash the Fingerprints (Recommended)

Replace the raw concatenated string with a fixed-length hash (e.g., SHA-256) before storing in `history.xlsx`.

**Pros:**
- Fixed-length output regardless of row size — completely eliminates the cell limit issue
- Minimal frontend code change — only the serialization step needs updating
- No change to matching logic — same input always produces the same hash

**Cons:**
- Existing `history.xlsx` files with old-format fingerprints would become incompatible — need a one-time migration or clear
- Hashes are not human-readable if anyone inspects `history.xlsx` for debugging
- **Backend impact: needs verification** — if the backend reads `history.xlsx` and compares fingerprints against its own raw strings, hashing would break that comparison. The backend would need to either:
  - Also hash its fingerprints when comparing against history entries, OR
  - Not read `history.xlsx` at all (in which case no backend change is needed)

### Option 2: Reduce Fingerprint Columns

Limit `generateFingerprint` to only key identifying columns (e.g., policy number, amount, date) instead of every non-excluded column.

**Pros:**
- Shorter fingerprints, less likely to hit the limit
- More readable and predictable fingerprints
- Simpler to debug

**Cons:**
- Does not guarantee the issue won't recur — large batches could still exceed the limit
- Risk of fingerprint collisions if key columns aren't unique enough
- Requires careful selection of which columns are sufficient for identification
- **Backend impact: needs verification** — if the backend generates full fingerprints and compares against history, a reduced frontend fingerprint would not match

### Option 3: Split Large Arrays Across Multiple Cells or Rows

Chunk fingerprint arrays so that no single cell exceeds the character limit.

**Pros:**
- Preserves the full raw fingerprint data
- No risk of collisions or compatibility issues

**Cons:**
- Adds significant complexity to both read and write logic
- Makes `history.xlsx` structure harder to understand and maintain
- Fragile — chunk boundaries depend on cell size calculations
- **Backend impact: needs verification** — if the backend reads history, it would also need to understand the chunked format

## Recommendation

**Option 1 (hashing)** is the cleanest solution. It eliminates the problem entirely with minimal code change and no risk of recurrence.

## Action Needed From Backend Team

Before implementing, confirm:

1. **Does the backend read `history.xlsx`?** If not, no backend changes are needed for any option.
2. **If yes, does it compare fingerprints from `history.xlsx` against its own generated fingerprints?** If so, the backend would need to adopt the same hashing approach (Option 1) or the same reduced column set (Option 2).
